# Compact Node Types Schema Reference (`compact-node-types.yaml`)

This document defines the structure, typing syntax, and validation invariants for `compact-node-types.yaml`, generated by [`CompactNodeTypes`](file:///home/michael/projects/go/tree-sitter/internal/tree-sitter/build/compact.go) and audited by [`ValidateCapture`](file:///home/michael/projects/go/tree-sitter/internal/tree-sitter/build/compact.go).

---

## 1. Overview & Purpose

The compact node types format is a token-efficient, lossless YAML representation of Tree-sitter's AST grammar schema. It translates Tree-sitter's verbose `node-types.json` into a concise dictionary designed for:
1. **LLM Context Optimization**: Reducing AST schema prompt token consumption by 60% to 83% to prevent AI context rot.
2. **Semantic Preservation**: Preserving all named and anonymous identities, requiredness, multiplicity, operator alternatives, and metadata (`root`, `extra`).
3. **Lossless Verification**: Guaranteeing 100% bidirectional correspondence with `node-types.json`.

---

## 2. Document Layout

A valid `compact-node-types.yaml` document consists of up to three root-level sections: `tokens:`, `supertypes:`, and `nodes:`.

```yaml
# Compact Tree-sitter Node Types (Generated from node-types.json)
# Legend:
#   tokens: [...]   : inventory of bare anonymous tokens
#   name            : named node declaration or reference
#   "token"         : anonymous token declaration or reference
#   key?            : optional field or children (omitted ? means required)
#   [T]             : multiple occurrences allowed (omitted brackets means single)
#   T1 | T2         : alternative types
#   root: true      : grammar root node
#   extra: true     : extra node (can appear anywhere, e.g. comments, whitespace)

tokens: ["!=", "%", "+", "-", ...]

supertypes:
  <supertype_name>: [<subtype_name_1>, <subtype_name_2>]

nodes:
  <node_type_name>:
    root: true       # optional metadata
    extra: true      # optional metadata
    fields:
      <field_name>: <type_expression>
      <optional_field_name>?: <type_expression>
    children: <type_expression>
    children?: <type_expression>
```

## 3. Section Specifications

### 3.1. `tokens` Sequence

An alphabetically sorted JSON/YAML flow sequence of bare anonymous tokens that appear as distinct declarations in `node-types.json` without extra fields, children, or metadata.
- Example: `tokens: ["!=", "%", "*", "+", "-", "/", "and", "or"]`
- Distinguishes anonymous tokens (e.g. `"await"`) from named nodes of the same spelling (e.g. named `await:` in `nodes:`).

### 3.2. `supertypes` Mapping

Defines Tree-sitter abstract node categories (such as `expression`, `pattern`, `primary_expression`) and their concrete subtypes using token-efficient flow sequence notation (`[...]`).
- **Key**: String identifier of the supertype.
- **Value**: Alphabetically sorted bracketed flow sequence of type identifiers (bare identifiers for named nodes, quoted strings for anonymous tokens).

#### Example
```yaml
supertypes:
  expression: [as_pattern, boolean_operator, comparison_operator, conditional_expression, lambda, named_expression, not_operator, primary_expression]
```

### 3.3. `nodes` Mapping

Defines every named AST node produced by the parser, as well as anonymous records that carry metadata (`root`, `extra`), fields, or children.
- **Key**: Bare identifier for named nodes (quoted if YAML keywords, e.g. `'true':`, `'false':`), or double-quoted string for anonymous nodes (e.g. `'"comment"'`).
- **Value**: Mapping containing optional metadata flags (`named: false`, `root: true`, `extra: true`), `fields:`, and `children:`/`children?:`.

| Attribute | Type | Description |
| :--- | :--- | :--- |
| `named` | boolean | Set to `false` only if the node declaration in `node-types.json` has `named: false`. |
| `root` | boolean | Set to `true` if the node is marked `root: true` in `node-types.json`. |
| `extra` | boolean | Set to `true` if the node is marked `extra: true` in `node-types.json`. |
| `fields` | mapping | Named fields accessible on the AST node. |
| `children` | string (type expression) | Permitted children when required (`required: true`). |
| `children?` | string (type expression) | Permitted children when optional (`required: false`). |

## 4. Type Expression & Multiplicity Grammar

Field values and `children` definitions preserve both `required` and `multiple` independently:

| Notation | Required | Multiple | Meaning | Equivalent JSON Descriptor |
| :--- | :--- | :--- | :--- | :--- |
| `key: T` | `true` | `false` | Exactly one required instance of `T` | `{"required": true, "multiple": false, "types": [...]}` |
| `key?: T` | `false` | `false` | Optional single instance of `T` | `{"required": false, "multiple": false, "types": [...]}` |
| `key: [T]` | `true` | `true` | One or more occurrences of `T` | `{"required": true, "multiple": true, "types": [...]}` |
| `key?: [T]` | `false` | `true` | Zero or more occurrences of `T` | `{"required": false, "multiple": true, "types": [...]}` |

The same convention applies to `children:` vs `children?:`:
- `children: [T]`: Required children group, multiple occurrences allowed.
- `children?: [T]`: Optional children group, multiple occurrences allowed.
- `children: T`: Required single child.
- `children?: T`: Optional single child.

### Named vs Anonymous References
- **Named nodes**: Unquoted identifiers (e.g. `expression`, `identifier`, `block`).
- **Anonymous tokens**: Double-quoted strings (e.g. `"+"`, `"-"`, `"and"`, `"or"`, `","`).
- **Alternative unions**: Joined by ` | ` (e.g. `'"and" | "or"'`, `'["," | expression]'`).

## 5. Lossless Validation Invariants

[`ValidateCapture`](file:///home/michael/projects/go/tree-sitter/internal/tree-sitter/build/compact.go) enforces strict bidirectional equivalence between `node-types.json` and `compact-node-types.yaml`:

1. **Declared Identities**: Every pair `(type, named)` declared in `node-types.json` is preserved—either in `tokens:` (bare anonymous tokens) or in `nodes:`.
2. **Supertype Coverage**: Every supertype declared in JSON must exist in YAML with identical, sorted subtype sequences. No extra or omitted supertypes are permitted.
3. **Field Parity**:
   - Every field in JSON must exist under the node's `fields:` block in YAML.
   - Optional fields (`required: false`) end with `?` in the YAML key.
   - Required fields (`required: true`) do not end with `?`.
   - Multiplicity (`multiple: true`) is enclosed in brackets `[...]`.
   - All referenced type alternatives preserve their exact named vs anonymous identity.
4. **Children Parity**:
   - A node with required children has `children:`.
   - A node with optional children has `children?:`.
   - All child type alternatives and multiplicity are verified.
5. **Metadata Preservation**: `root: true` and `extra: true` are checked for exact correspondence.
6. **No Extraneous Types or Unknown Properties**: Parsing `node-types.json` rejects unknown properties. No node, field, or supertype may exist in YAML that is not defined in `node-types.json`.

## 6. Comparison: JSON vs. Compact YAML

### Raw `node-types.json` (51 lines, ~320 tokens)
```json
[
  {
    "type": "binary_operator",
    "named": true,
    "fields": {
      "left": {
        "multiple": false,
        "required": true,
        "types": [
          {
            "type": "primary_expression",
            "named": true
          }
        ]
      },
      "operator": {
        "multiple": false,
        "required": true,
        "types": [
          {
            "type": "+",
            "named": false
          },
          {
            "type": "-",
            "named": false
          }
        ]
      },
      "right": {
        "multiple": false,
        "required": true,
        "types": [
          {
            "type": "primary_expression",
            "named": true
          }
        ]
      }
    }
  }
]
```

### Generated `compact-node-types.yaml` (6 lines, ~30 tokens)
```yaml
nodes:
  binary_operator:
    fields:
      left: primary_expression
      operator: '"+" | "-"'
      right: primary_expression
```

**Net result:** ~80% token reduction while retaining full structural semantics, complete operator alternatives, and named/anonymous distinctions.
